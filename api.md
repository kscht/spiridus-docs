# REST API

Адрес — `https://v2.spiridus.ru/api/v1/`. Описание в OpenAPI 3.1 — [`/api/v1/openapi.json`](https://v2.spiridus.ru/api/v1/openapi.json):
спецификация описывает все REST-инструменты, но не все прямые адреса.
`projects/*`, `files/blob/*`, `private/*`, скачивание загрузок, приглашения, подтверждение и вход
описаны ниже вручную; передача модели только OpenAPI эти сценарии не покрывает.

Инструменты — те же, что у [MCP](mcp.md): у каждого свой адрес, аргументы — тело запроса JSON.

## Вход

Ключ из регистрации ([getting-started.md](getting-started.md)) — в заголовке:

```
Authorization: Bearer sp_...
```

| Адрес | Что |
|---|---|
| `POST /api/v1/register` `{ "email": …, "nickname": … }` | письмо со ссылкой подтверждения; на v2.spiridus.ru обычная регистрация закрыта, нужен путь по приглашению |
| `GET /api/v1/me` | кто я и мои лимиты |
| `DELETE /api/v1/me` | удалить свою запись — только основным ключом; владелец совместного проекта сначала передаёт владение или дожидается удаления проекта (иначе 409); без обработчиков/реестра 503 |
| `GET /api/v1/keys` | свои ключи без секретов: имя, начало ключа, права, адреса, срок, последнее использование |
| `DELETE /api/v1/keys/<id>` · `…/others` · `…/all` | отозвать себя; другой ключ, все кроме текущего или все сразу — только основным ключом |
| `GET /api/v1/tools` | инструменты со схемами аргументов (JSON Schema); без ключа |
| `POST /api/v1/tools/<имя>` | вызвать инструмент |
| `POST /api/v1/tools/<имя>?async=1` | вызвать, не дожидаясь: сразу номер задачи |
| `GET /api/v1/jobs` | свои задачи |
| `GET /api/v1/jobs/<id>?wait=N` | состояние и результат задачи; `wait` — сколько секунд подождать готовности, не больше 60 (в примерах — 30) |
| `DELETE /api/v1/jobs/<id>` | отменить задачу |
| `POST /api/v1/files?name=<имя>` | загрузить свой файл (тело запроса — файл, до 32 МБ) → ссылка `upload:<id>/<имя>` |
| `GET /api/v1/files` · `DELETE /api/v1/files/<id>` | свои файлы и занятое место; удалить |
| `GET /api/v1/files/<id>/<имя>` | скачать свою загрузку с ключом владельца и правом `files`; чужая ссылка доступа не даёт |
| `GET /api/v1/origins` · `POST` · `DELETE` `{ "origin": … }` | сайты, с которых ваши страницы зовут API из браузера |
| `GET /api/v1/projects` | свои проекты с ролями, ожидающие приглашения и передачи владения |
| `GET /api/v1/projects/<slug>` · `…/articles/<путь>` | дерево и статья текущей головы `main` (ссылки статьи на ресурсы — на `files/`) |
| `GET /api/v1/projects/<slug>/files/<путь>` | исходник `.md` — 200 `text/markdown`; ресурс — 302 на подписанную ссылку (до 15 минут) |
| `GET /api/v1/openapi.json` | описание API; без ключа |
| `GET /api/v1/openapi-chat.json` | то же для чатов: только инструменты модели; `?tools=a,b` — свой набор |

На `v2.spiridus.ru` регистрация по приглашениям. `GET /invite/<token>` — форма, `POST` на тот же
адрес с email/nickname отправляет письмо; `GET /api/confirm?t=…` показывает подтверждение,
`POST /api/confirm` с `t` завершает его. Для `register`, `confirm`, `me`, `login`, `logout`, `block`
есть также адреса `/api/v1/…`. Удаление записи удаляет единоличные проекты и `/d` со всей историей;
вклад/ресурсы в чужих проектах остаются. [Условия удаления](data.md#сколько-хранится).

Регистрация возвращает HTTP 409 «nickname занят, выберите другой» для любого занятого имени,
включая имя владельца указанного email. Для перевыпуска основного ключа получите действующее приглашение у владельца и укажите тот же email и любое свободное
имя: при подтверждении сохранится прежний nickname. Подробнее — [первые шаги](getting-started.md#1-зарегистрируйтесь).

### Ключи

Ключ из регистрации — **основной**: все права, без срока, с любого адреса. Для программ, машин и CI
лучше выдать отдельные ключи — на странице [«Ключи»](https://v2.spiridus.ru/api/keys) (в браузере, вход
основным ключом). До 20 ключей на учётную запись. У каждого ключа:

- **имя** — «ноутбук — git», «Claude Desktop», «CI сборки»;
- **права**: `mcp` — инструменты через MCP; `rest` — этот API; `files` — свои загрузки (`/api/v1/files`,
  `files_*` и ссылки `upload:` во входе любого инструмента); `docs` — опубликованные документы (`document_*`,
  `documents_*`); `git:read`, `git:write` —
  зарезервированы и сейчас ничего не открывают. Права только сужают то, что можно учётной записи: роль в
  проекте ключ не расширяет. Права на отдельные проекты (`project:<id>:read|write`) — следующим шагом;
- **срок** — 30, 90 (по умолчанию) или 365 дней либо явно «бессрочный»; за неделю до истечения приходит письмо;
- **адреса** — по желанию: IPv4, IPv6 или подсети CIDR (`203.0.113.7`, `2001:db8::/48`), до 20. Допустимые длины CIDR: IPv4 `/8`–`/32`, IPv6 `/16`–`/128`. С другого
  адреса ключ получает 401 «ключ не действует с этого адреса» — это не отзыв, ключ цел;
- **последнее использование** — когда и с какого адреса. Адрес хранится только у ключа: узкий ключ
  видит свой `lastIp`, основной — адреса всех своих ключей.

`project_import` требует право `docs`, как чтение собственных опубликованных документов.

Сохранённое — задачи `/api/v1/jobs`, файлы `private:` и сеансы — ключ видит, только если у него есть права,
которые понадобились для их получения: задача `files_list` основного ключа (или `code_run`, внутри которого
был `files_list`) ключу без `files` не видна ни в списке, ни по id; шаг в сеансе, где код читал загрузки, —
тоже только с `files`. Сеанс, открытый до перезапуска шлюза, продолжает только основной ключ.

Хранится только sha256 ключа и первые знаки (`sp_ab12…`) — для узнавания; сам ключ показывается **один раз**,
на странице после создания, и по почте не приходит (приходит письмо, что ключ создан). Новый ключ выдаётся
только на странице: через API и MCP — список и отзыв, без новых секретов.

Узкий ключ может отозвать только себя по своему id. Отзыв другого ключа, `others` и `all` разрешён
только основным ключом. Отзыв действует на следующем же запросе.
Основной ключ можно отозвать, если есть другие. Повторная регистрация той же почтой через действующее приглашение выдаёт новый основной
ключ: прежний основной перестаёт работать, остальные ключи остаются — отзовите их явно, если нужно.
На сайт (кука) входят только основным ключом: у сеанса сайта своё правило, адреса для него не проверяются.
Удалить учётную запись можно только основным ключом; с ней удаляются все ключи.

**Вход на сайт:** `POST /api/login` с JSON `{key}` (основной ключ) ставит куку `HttpOnly`,
`SameSite=Strict`; форма есть на `/` и `/p/`. `POST /api/logout` завершает вход.
`POST /api/project-invitations` с `{id, action:"accept"|"decline"}` — ответ на приглашение
через сайт с основным ключом или кукой и допустимым Origin; это отдельный маршрут,
вне `POST /api/v1/tools/invitations` с обычными аргументами инструмента.

**На сайте** (живой редактор, страница документа) кнопка «↻ пересчитать» у блока может попросить ключ:
он запоминается в куке этого сайта (`HttpOnly`, `SameSite=Strict`), в странице и в ссылках его нет. Кука
годится только для пересчёта блоков, ответа на приглашение в проект и чтения
проектов на страницах `/p/…` (`GET /api/v1/projects…`); инструменты, файлы и удаление учётной записи — только
с ключом в заголовке `Authorization`. Выйти — `POST /api/logout`. Без права на проект, без входа и на
несуществующий проект ответ `/api/v1/projects/…` один — 404. На страницах проектов пересчёта блоков пока
нет: кнопок там нет, а `POST /api/block` со страницы `/p/…` отвечает 403. Сбои живых блоков страница проекта
на `/api/events` не шлёт; шлюз и сам хранит текст ошибки только от публичных страниц (Referer не `/p/…`).

**Без ключа — гостем** на прежних `/d` (не `/p`) читатель пересчитывает модель с другими параметрами: блок ```` ```freecad ````
(таблица параметров, `cad_recompute`) и ```` ```modelica ```` со строками `// set:` (поля ввода под
исходником). Гостю можно только то, что уже посчитано с ключом: FreeCAD — тот же документ FCStd из
результатов сервера, Modelica — тот же текст модели, что в её результате `// result:`; меняются только
значения параметров. Модель правили — пересчёт после входа. По умолчанию — до 300 таких пересчётов в час с адреса; это настройка установки,
а не постоянная гарантия. Есть также пробные HLSL/Lean без сохранения результата;
у них отдельные пределы исходника и частоты ([HLSL](blocks/hlsl.md), [Lean](blocks/lean.md)).

Прямой `POST /api/block` (также `/api/v1/block`) принимает `{lang, source, attrs?, context?}`:
`lang` — серверный язык блока, `source` — исходник, `attrs` — строковые атрибуты забора,
`context` — до 19 дополнительных исходников; вместе до 256 КиБ UTF-8, тело до 1 МиБ.
Готовое из кеша возвращается без ключа и расхода квоты: `{ok:true, cached:true, result}`.
Новый расчёт требует входа, кроме перечисленных гостевых случаев. Это маршрут кнопки
пересчёта, не универсальная замена `tools/<имя>`; со страницы `/p` он отказывает 403.

## Вызов инструмента

```sh
curl -sS -X POST https://v2.spiridus.ru/api/v1/tools/render_block_docs \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"lang": "mermaid"}'
```

Ответ:

```json
{ "ok": true, "data": …, "content": [ … ] }
```

- `data` — полный `structuredContent` типизированного инструмента; у остальных — JSON первого
  текстового ответа. У `render_block_docs` — `null`, справка находится в `content`;
- `content` — ответ целиком, как у MCP: `text`, `image` (base64), `resource_link`;
- неверные аргументы — HTTP `400` со списком `issues`; ошибка инструмента — обычно HTTP `422` и
  `ok: false`, временная занятость — `503` ([ошибки](#ошибки)).

Тело — аргументы инструмента. Что принимает каждый (опции песочниц, сборка `build`, ссылки на файлы,
пределы) — [arguments.md](arguments.md); машинно — `GET /api/v1/tools` и `openapi.json`.

## Свои файлы

Модель STL для Blender, проект QElectroTech, документ Markdown — загрузите файл и подставьте ссылку в
аргументы инструмента:

```sh
curl -sS -X POST 'https://v2.spiridus.ru/api/v1/files?name=model.stl' \
  -H "Authorization: Bearer $SPIRIDUS_KEY" --data-binary @model.stl
# {"ref":"upload:4c23262dcc968948/model.stl","id":"4c23262dcc968948","name":"model.stl","size":105,"existed":false}
```

| Куда | Аргумент |
|---|---|
| `blender_run` | `"inputs": ["upload:…/model.stl"]`, в сценарии — `load("model.stl")` |
| `qet_run` | `"project": "upload:…/shema.qet"` |
| `qet_call` | `"put": {"shema.qet": "upload:…/shema.qet"}` |
| `render_check` | `"markdown_file": "upload:…/doc.md"` — вместо `markdown` |

Файлы видны только вам. Один и тот же файл второй раз места не занимает: ссылка зависит от
содержимого, поэтому и готовый результат по ней берётся из кеша. Место — до 500 МБ, файл — до 32 МБ
(Blender принимает входной файл до 24 МБ, документ для `render_check` — до 512 КБ). Через MCP — инструмент
`files_upload` с содержимым в base64, до 10 МБ.

**Файл в документ.** Загрузки `upload:` и большие ответы Code Mode `private:` читатель не видит.
`private:` доступен владельцу через инструменты и временный подписанный адрес не дольше 15 минут.
Чтобы показать файл читателю, явно опубликуйте его; для загрузок разрешены картинки (PNG, JPG, WebP,
GIF, SVG) и шрифты, приватный результат копируется как файл. Предел **10 МиБ** действует
и для `upload:`, и для `private:`:

```sh
curl -sS -X POST https://v2.spiridus.ru/api/v1/tools/files_publish \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"ref": "upload:4c23262dcc968948/photo.png", "alt": "Схема стенда"}'
# data: {"artifact":"…","ref":"artifact:…/photo.png","url":"https://v2.spiridus.ru/artifacts/…/photo.png","markdown":"![Схема стенда](artifact:…/photo.png)"}
```

В `ref` можно передать также собственный `private:<id>/<имя>`. Строку `markdown` вставляют в документ;
`render_check` и `document_share` отвергают необработанный `private:` и подсказывают `files_publish`.
Опубликованный файл виден по ссылке без ключа, как
результаты инструментов, и живёт, пока жива учётная запись; снять раньше — `files_unpublish`
`{"ref": "artifact:…/photo.png"}`. Тип проверяется по содержимому, а не по имени.

## Поделиться документом

Основной путь — [проект и приглашение](projects.md).
Новый документ сохраняют статьёй проекта. Узнайте проект через `projects`, прочитайте дерево
через `project_read` и передайте `commit` ответа как `base`. Нужна роль не ниже editor:

```sh
curl -sS -X POST https://v2.spiridus.ru/api/v1/tools/project_read \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"project":"atlas","op":"tree"}'
# Возьмите data.commit ответа и подставьте вместо <commit>:
curl -sS -X POST https://v2.spiridus.ru/api/v1/tools/project_write \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"project":"atlas","base":"<commit>","op":"put","files":[{"path":"Начало.md","content":"# Начало\n\nДокумент проекта."}]}'
```

Дайте человеку `/p/atlas/Начало.md` из ответа и пригласите его через
`invitations({project:"atlas", action:"invite", email, role})` (владелец или админ). Человек принимает
приглашение на `https://v2.spiridus.ru/p/` или через `invitations({action:"accept", id})` и входит на сайт.
Без проекта и права создавать проекты попросите
владельца системы пригласить вас. [Формат статьи](markdown.md), [права и операции](mcp.md#проекты).

`document_share` обновляет только свой прежний `/d`: передайте `id` из `documents_list`.
Без `id` новый документ не создаётся, REST вернёт HTTP 422. Пример обновления:

```sh
curl -sS -X POST https://v2.spiridus.ru/api/v1/tools/document_share \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"id": "<id из documents_list>", "markdown": "# Схема\n\n```mermaid\nflowchart LR\n  A --> B\n```\n"}'
# data: {"id":"4ZcR…","version":"6324238542fc","versions":1,"url":"https://v2.spiridus.ru/d/4ZcR…",…}
```

- Ссылка `url` открывается **без ключа** — у любого, кому вы её дали; в поисковики страница не отдаётся.
- `editUrl` — тот же документ в живом редакторе Spiridus: исходник слева, документ справа, правки видны
  сразу. Редактор живёт на `live-stage.spiridus.ru` — это его рабочий адрес, а не тестовый стенд.
  На странице документа это ссылка «✎ Редактировать». Опубликованный документ правки там не меняют —
  сохраните правку через `document_share` с прежним `id` или статьёй проекта.
- Поправили документ — вызовите снова с `"id": "<id>"`: новая версия по той же ссылке. Прежние
  версии остаются: `…/d/<id>?v=<version>`. Тот же текст второй раз версии не добавляет.
- Менять и удалять документ может только тот, кто его опубликовал.
- Документ с ключом `sp_…` в тексте не публикуется: его увидел бы каждый, у кого ссылка. Пишите в примерах
  `$SPIRIDUS_KEY`.
- Документ — строкой `markdown` или файлом `markdown_file` (`upload:…/doc.md`), до 512 КБ; документов —
  до 200 на учётную запись.
- Блоки, которые рисует сервер, показывают готовые результаты (`result: artifact:…`) — сначала
  проверьте документ `render_check`. Свои файлы (`upload:…`) читатель ссылки не увидит: они только с ключом.
- Документов много и непонятно, что где, — `documents_catalog` даёт одну ссылку на каталог: таблица всех
  ваших документов (заголовок со ссылкой, начало текста, когда изменён, сколько версий, ✎ в редактор).
  Каталог — такой же документ по ссылке `/d/<id>` и обновляется сам, когда вы публикуете или удаляете
  документ. Ссылка на каталог открывает и ссылки на все документы; утекла — `{"rotate": true}` даёт новую,
  старая перестаёт открываться.

Без ключа читаются и сами документы — для своих программ:

| Адрес | Что |
|---|---|
| `GET /api/v1/docs/<id>.md` | текст документа; `?v=<version>` — версии |
| `GET /api/v1/docs/<id>` | заголовок, когда создан и изменён, версии с датами |

## Асинхронные вызовы

Инструменты с песочницами (`plantuml_run`, `hdl_synth`, `modelica_run`, `cad_run`, `blender_run`…)
работают от секунд до минут и ждут в общей очереди. Чтобы не держать соединение:

```sh
# поставить задачу — ответ сразу, 202 и номер
curl -sS -X POST 'https://v2.spiridus.ru/api/v1/tools/plantuml_run?async=1' \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"source": "Alice -> Bob: привет"}'
# {"id":"91818451…","status":"queued","poll":"/api/v1/jobs/91818451…?wait=30"}

# забрать результат: wait=30 — ждёт готовности до 30 с (можно до 60), иначе отвечает status: queued или running — спросите ещё раз
curl -sS "https://v2.spiridus.ru/api/v1/jobs/91818451…?wait=30" -H "Authorization: Bearer $SPIRIDUS_KEY"
```

`status` — `queued`, `running`, `done` (результат — в `result`, как у обычного вызова), `error`, `cancelled` или
`lost` (шлюз перезапустился до передачи расчёта в песочницу либо сборка не поддерживает отвязанные задания).
Продолжайте опрос, пока `status` — `queued` или `running`; `done` — успех,
`error`, `cancelled`, `lost` — завершение без результата.
Одноразовые CPU-расчёты с отвязанным маршрутом продолжают работу после перезапуска шлюза. Запись и
готовый результат переживают перезапуск шлюза. Ответ больше 64 КиБ возвращается ссылкой `private:` и
свежим временным `url`; подпись URL в записи задания не хранится.
Готовые задания хранятся семь дней. У отвязанных заданий `queued` сохраняется до допуска планировщика узла; `queue` содержит
только `{class, position, ahead}` в своей доле (`batch` либо `interactive`, включая `check`), без чужих id.
`node` — узел расчёта, `waitMs` — ожидание до старта, `ms` — всё время задания от постановки до окончания;
все длительности в миллисекундах. До выбора узла или при отсутствии сведений об очереди `queue` отсутствует.
Для GPU, сеансов и режимов без независимого фонового исполнения `running` и `startedAt` фиксируются
перед отправкой запроса исполнения, без точной позиции очереди. Инструменты шлюза без песочницы
переходят в `running` перед запуском обработчика. Время первого старта сохраняется для всего задания;
вложенные запуски `code_run` не меняют его узел и не выдают свой `sandboxJobId` в его статусе.
Квота частоты списывается до ответа 202, в том числе при попадании в кеш; при исчерпании — 429 без задания. Исполнение и восстановление
повторно её не расходуют; при отмене, ошибке и `lost` списание не возвращается (подробнее — [Code Mode](code.md#фоновые-задания)).
Права `private:` проверяются по владельцу/проекту и метке результата, как у синхронного вызова;
сам префикс `private:` не требует `files`. `upload:` и `blob:` требуют `files`.

Картинки ответа (`image` в `content`, например кадры `blender_run`) в результате задания не хранятся
base64: шлюз кладёт их приватными файлами владельца с теми же правами, что результат, а в `content`
оставляет `{type: "image_ref", ref: "private:<id>/image-1.png", mimeType, bytes}`. Файлы живут, пока
живёт запись задания. Посмотреть — `image_view` (`POST /api/v1/tools/image_view`, `{ref, max}`):
вход PNG/JPEG/SVG до 20 МиБ; уменьшенная копия со стороной до 1024 px и размером до 192 КиБ.
В Code Mode `image_view` возвращает только метаданные.

Задание связано с ключом, которым его поставили, в том числе из Code Mode. До запуска и восстановления
после перезапуска, раз в секунду во время работы и перед сохранением ответа шлюз проверяет, что ключ
ещё действует. Отзыв, истечение срока или блокировка записи отменяют задание (`cancelled`); отмена
отправляется в песочницу с повторами при сбое связи. Если связь не восстановится, расчёт там может
продолжаться до собственного срока: остановить недоступную песочницу шлюз не может, но результат уже
не принимает. Готовые результаты остаются доступны другим ключам владельца с нужными правами.
У старых заданий, сохранённых до появления привязки к id ключа, определить исходный ключ невозможно:
они продолжаются с сохранёнными правами; их можно отменить явно по id задания.

`DELETE /api/v1/jobs/<id>` возвращает только статус и метаданные, в том числе для уже завершённого
задания. Результат, его ссылки и текст ошибки доступны через `GET`, с проверкой прав ключа.
Скрипт целиком — [`examples/async.sh`](examples/async.sh), на Python — [`examples/spiridus.py`](examples/spiridus.py).

Эти же задания доступны через MCP `job_status({job, wait})` (до 30 с) и `job_cancel({job})`.
Из Code Mode постановка — `tools.<имя>.start(args)` → `{job}`, чтение —
`tools.jobs.get(id, {wait: 30})`, отмена — `tools.jobs.cancel(id)`; сценарий может завершиться
раньше задания. Владелец, права и лимиты общие для всех входов, гость фон не запускает.
Инструменты проектов напрямую в фон не ставятся. Расчёт из сценария, уже читавшего проект,
сохраняет приватность проекта и пометку журнала. Примеры — [Code Mode](code.md#фоновые-задания).

## Кеш результатов

Инструменты, которые рисуют и считают в песочнице, запоминают ответ: `plantuml_run`, `structurizr_run`,
`quantum_run`, `hdl_synth`, `hdl_sim`, `modelica_run`, `cad_run`, `blender_run`, `ffmpeg_run` (сборка NVENC), `tts_run`, `qet_run`, `text_parse`.
Тот же вызов второй раз отвечает сразу, из кеша:

- **ключ** — инструмент, все аргументы побайтно (комментарий в сценарии, пробел, порядок строк — уже
  другой вызов; порядок полей JSON — нет) и сборка с точным образом программы. Поле `task` в ключ не
  входит;
- **в ответе** — `"cached": true`, а `ms` и остальное — из того запуска, который посчитал результат;
- **ответ из кеша** не ждёт очереди. Синхронный вызов не тратит лимит вызовов;
  принятые `.start` и REST `async=1` расходуют квоту и при попадании в кеш;
- **ошибки не запоминаются**: упавший вызов повторяется заново;
- **посчитать заново** — изменить что угодно в аргументах (хоть комментарий) или назвать другую сборку
  `build`; новая сборка программы и пересобранный образ дают новый ключ сами.

GPU-сборки используют тот же кеш: повтор TTS с тем же `seed`, Blender GPU или ffmpeg NVENC
возвращает сохранённый набор файлов. Проектные вызовы разделены по проекту, вызывающему и коммиту.

`render_check` не кешируется: он каждый раз рисует документ. Его проверки линтерами и текста
запоминаются на 10 минут для того же документа и той же сборки.

## Лимиты и очередь

Сейчас идёт **альфа-тестирование**: лимиты могут меняться; текущие — в `GET /api/v1/me`.

**На пользователя** (по ключу; в MCP и REST — общие):

| Что | Предел |
|---|---|
| вызовов в час — тяжёлых (рисование на сервере, `render_check`) | 600 |
| вызовов в час — лёгких (справка, примеры, файлы) | 6000 |
| обычных вызовов одновременно | 2 |
| асинхронных задач | 5 незаконченных; до 1000 записей и 256 МБ записей на пользователя; готовые хранятся 7 дней |
| приватных результатов | 2 ГиБ (2 147 483 648 байт), вместе с закреплёнными HLS, большими ответами и картинками фоновых заданий |
| своих файлов | 500 МБ, до 5000 файлов |
| опубликованных документов | 200, каждый до 512 КБ |
| сайтов для вызовов из браузера | 10 |
| частота запросов с одного адреса | REST — 2 в секунду, кратковременно до 20–50 сразу; MCP — 20 в секунду |

Пределы проектов, путей и приглашений — [projects.md](projects.md#пределы-и-имена).

`GET /api/v1/me` возвращает `limits.privateResults: {limitBytes, usedBytes, remainingBytes}`:
все ключи владельца делят одну квоту приватных файлов. В учёт входят также резервы
текущих записей; служебные метки не считаются. Предел настраивает администратор
(по умолчанию 2048 МиБ).
Место для всего набора резервируется до записи и открытия потоков. Превышение —
HTTP **507**, в MCP текст `507: Квота приватных результатов…`: нужные байты, доступное
место и предел. Сохранённые результаты при этом не удаляются. У уже принятого с 202
задания будет `status: error` с причиной `507: …`; сам опрос остаётся HTTP 200.
Квота записей заданий (256 МБ) отдельная, приватные файлы в неё не входят.
Файлы заданий закреплены до TTL (семь дней); после него HLS может оставаться до
общей уборки. Личная квота не вызывает уборку автоматически — [сроки хранения](data.md#приватные-результаты-и-место).

**Размеры запроса:**

| Что | Предел |
|---|---|
| тело вызова REST (`/api/v1/tools/…`) | 2 МиБ; `project_write` и `project_import` — 16 МиБ |
| файл через `POST /api/v1/files` | 32 МБ |
| тело запроса MCP | 16 МБ; файл через `files_upload` — до 10 МБ (в base64) |
| документ `render_check` (строкой или файлом) | 512 КБ |
| исходник PlantUML, Structurizr, Modelica, сценарий FreeCAD и Blender | 256 КБ |
| исходник HDL | 512 КБ, или до 32 файлов по 512 КБ (вместе до 2 МБ) |
| программа OpenQASM | 128 КБ |
| текст `text_parse` | 20 000 знаков, разбираются первые 60 предложений |
| входной файл Blender | 24 МБ, до 8 файлов, вместе до 32 МБ |

**Время работы** одного вызова на сервере (дольше — прерывается, ответ — ошибка «время»):

| Инструменты | Предел |
|---|---|
| `render_check` | 180 с |
| `plantuml_run`, `quantum_run`, `cad_run` | 120 с |
| `structurizr_run`, `modelica_run`, `qet_run`, `qet_call` | 180 с |
| `text_parse` | 150 с |
| `hdl_synth`, `hdl_sim`, `blender_run` | 300 с |

К этому добавляется ожидание в очереди: обычный синхронный вызов ждёт ответа до 300 с всего,
долгие — асинхронно ([асинхронные вызовы](#асинхронные-вызовы)). Для `code_run` ожидание
допуска ограничено отдельно 300 с, исполнение после допуска — 300 с; с запасом на остановку
синхронный вызов может занять около 610 с. Сервер ждёт ответа до 630 с; клиенту нужен соответствующий timeout.

**Очередь.** Песочницы — одна очередь на всех. Кто много потратил за последние полчаса-час, стоит в ней
дальше тех, кто тратит мало, — но не вечно: ожидание его поднимает. Одинаковый вызов берётся из
кеша сразу, без очереди; расход квоты зависит от синхронного или фонового способа вызова
([кеш результатов](#кеш-результатов)).

**До входа** (регистрация): с одного адреса — 3 в час, на одну почту — 3 в сутки, всего — 50 в час;
подтверждений с адреса — 20 в час. Слишком часто — `429` и через сколько повторить.

## Форматы ответов

**Вызов инструмента** — `POST /api/v1/tools/<имя>`:

```json
{ "ok": true, "data": { … }, "content": [ { "type": "text", "text": "…" }, { "type": "image", "data": "…base64…", "mimeType": "image/png" } ] }
```

- `data` — полный структурированный результат типизированного инструмента; у остальных — JSON
  первого текстового ответа. У `render_block_docs` `data: null`, Markdown-справка находится в `content`;
- `content` — ответ целиком, как у MCP: `text`, `image` (картинки в base64), `resource_link` (ссылки на файлы);
- для чатов (`/api/v1/chat/tools/<имя>`, спецификация `openapi-chat.json`) — только результат: объект
  `data` или `{ "result": "текст" }`, без `content`;
- без картинок — `?images=0` (или заголовок `X-Spiridus-Images: off`): в `content` нет `image`, ссылки
  на картинки в `data` остаются. Для моделей без зрения; то же работает у MCP.

### Ошибки

До исполнения инструмента ответ — `{ "error": "…" }` с HTTP-кодом; при неверных аргументах
есть ещё `issues`. Ошибка уже исполненного инструмента имеет другой формат:
HTTP **422**, `{ "ok": false, "data": null, "content": [{"type":"text","text":"409: …"}] }`.
Число в начале текста (`403`, `404`, `409`, `413` и другие) — предметная причина, **не HTTP-статус**
обёртки. Например, конфликт `base` проекта — `409: …` в тексте HTTP 422.

| HTTP | Где и что означает |
|---|---|
| 400 | до исполнения: неверные JSON, схема аргументов или имя файла |
| 401 | нужен ключ; ключ отозван, истёк или не действует с этого адреса |
| 403 | запись заблокирована, сайт не добавлен (CORS) или у ключа нет нужного права (`mcp`, `rest`, `files`, `docs`) |
| 404 | нет маршрута, инструмента или объекта соответствующего прямого endpoint |
| 409 | прямой endpoint: занятый nickname или конфликт состояния загрузки |
| 413 | превышен размер тела или предел прямой загрузки |
| 415 | прямые загрузки: MIME не поддерживается или не совпал с содержимым |
| 422 | инструмент исполнился и вернул ошибку; причина — в `content` |
| 429 | допуск, частота или лимит; срок повтора ищите в `error`, заголовок `Retry-After` не обещается |
| 503 | возможность недоступна; временная занятость или недоступность вычислительных узлов сопровождается `Retry-After: 5` |
| 504 | ожидание ответа оборвалось; для `finish` повторите запрос с тем же id |

Постоянно ненастроенная возможность может отвечать 503 **без** `Retry-After`.
Это относится и к `code_run`, `session_open`, `session_call` и инструментам сеансов нотаций:
сборка есть, но её узлы упали или не принимают новые задания — временный отказ с `Retry-After: 5`.
Отсутствующая сборка, ошибка образа, неверный токен узла, несовместимый протокол
и недостаточный общий бюджет ресурсов остаются ошибками конфигурации без срока повтора.

Если выбрать узел не удалось, учитываются все кандидаты для запрошенной сборки
с достаточным **полным** бюджетом, включая сведения последней успешной пробы:

| Условие (первое совпавшее) | Классификация |
| --- | --- |
| Хотя бы один подходящий узел временно недоступен или в drain; либо временно недоступен узел без успешной пробы | Временный отказ, `Retry-After: 5` |
| Есть подходящий узел с постоянной ошибкой пробы (авторизация, протокол) | Исходная ошибка, без `Retry-After` |
| Сборка известна, но полный бюджет каждого её узла недостаточен | Постоянный отказ с требуемыми ресурсами и бюджетами, без `Retry-After` |
| Сборки или подходящего узла нет | Постоянный отказ, без `Retry-After` |

После падения всего пула сохранённый каталог по-прежнему подтверждает отсутствие сборки.
Узел с известным недостаточным полным бюджетом не превращает постоянную ошибку другого
кандидата во временную.

Отказ допуска из-за занятого бюджета ядер передаётся как 503 с `Retry-After: 5`;
признак временной занятости сообщает узел, одного HTTP 503 для него недостаточно.
Если исход уже отправленного шага сеанса неизвестен, автоматически повторять его нельзя;
такой отказ тоже не содержит `Retry-After`.
Для прямых адресов проектов и загрузок действуют их HTTP-коды; например, отсутствующий проект
отвечает 404. У инструментов те же предметные причины передаются через обёртку выше:
нехватка места на вычислительном узле — `507: …` в тексте HTTP 422.
Исчерпание квоты приватных результатов шлюза возвращает HTTP 507 до записи нового набора.
OpenAPI описывает 507, 503 и необязательный `Retry-After` для временного 503;
сверяйте статус и тело фактического ответа.

**Задача** (`?async=1`, `/api/v1/jobs/<id>`):

```json
{ "id": "91818451…", "tool": "plantuml_run", "status": "done", "queuedAt": "…", "finishedAt": "…", "ms": 2999, "waitMs": 250, "node": "default",
  "result": { "ok": true, "data": { … }, "content": [ … ] } }
```

`status` — `queued`, `running`, `done`, `error` (с текстом), `cancelled`, `lost`.

**Главное в `data` у инструментов:**

| Инструмент | Поля |
|---|---|
| `render_check` | `clean` — блоки собраны и сценарии `interact` прошли; виды из `strict` также влияют на итог, остальные замечания по умолчанию не меняют `clean`; `issues` — замечания `{ line, kind, text, hint, at }` (`at` — ширины окна; `hint` — у первого замечания каждого рецепта); `blocks`, `errors`; `artifact`, `files` — снимки; `preview` — снимок строкой Markdown; `show_user` — что сделать дальше. Картинки в ответе — только при замечаниях к рисункам или со сценариями `interact`. `brief: true` — без `hint`, `show_user` и `files`, картинки — только вырезы проблемных блоков |
| `plantuml_run`, `structurizr_run`, `quantum_run`, `hdl_synth`, `hdl_sim`, `modelica_run`, `qet_run` | `artifact` — id результата; `files` — ссылки на файлы; `block` (и `fence`) — готовые строки для блока документа, уже со сборкой; `warnings` или ошибка со строкой |
| `cad_run`, `blender_run` | `artifact`, `files` (модели, кадры); объём, габариты, объекты; `block` — блок ```stl со сборкой, если есть модель STL |
| все инструменты песочниц | `build` — id сборки, в которой посчитано (и без `build` в запросе), `buildImage` — sha256 её образа. Чтобы результат не менялся с новой версией программы, запишите сборку в документ — [blocks/sandbox.md](blocks/sandbox.md#как-закрепить-результат) |
| `text_parse` | `block` — готовый блок ```conllu; `parsers` — время и лицензия анализаторов |
| `render_examples` | `blocks` — примеры `{ lang, where, page, section, code, features }`; `recipes` — `{ lang, kind, do, ok }` |
| `render_block_docs` | справка Markdown (в `content`) |
| `files_upload`, `POST /api/v1/files` | `{ ref, id, name, size, existed }` — `ref` подставляют в аргументы |

## Вызовы из браузера: свой сайт

Для скриптов и серверных запросов не требуется добавлять Origin; авторизация и общие лимиты сохраняются. Если API зовёт **страница в браузере** — ваш Open WebUI,
своё приложение, — браузер пустит запрос, только если сайт записан к вашей учётной записи (CORS).
Добавьте его один раз — curl'ом или скриптом, не из этого браузера:

```sh
curl -sS -X POST https://v2.spiridus.ru/api/v1/origins \
  -H "Authorization: Bearer $SPIRIDUS_KEY" -H 'content-type: application/json' \
  -d '{"origin": "https://webui.example.org"}'
```

Сайт — схема, имя и порт, без пути: `https://webui.example.org`, `http://localhost:8080`. До 10 сайтов;
убрать — тот же запрос с `DELETE`. С сайта, которого нет в списке, запрос с вашим ключом получит `403`.
То же правило — для MCP.

## Типизированные результаты инструментов

У части инструментов MCP каталог tools/list содержит outputSchema. Полный объект результата
находится в structuredContent, а content содержит сводку, изображения и ссылки. Если
structuredContent отсутствует, используйте прежний текстовый ответ. Сводка не обязана быть JSON.

REST сохраняет прежние data и content; схема data в OpenAPI берётся из того же контракта ответа.
Справка render_block_docs остаётся текстом: MCP дополнительно возвращает `{result: текст}`,
REST data остаётся null, chat endpoint — `{result: текст}`. Ошибки isError остаются текстовыми.

`code_run`, `ffmpeg_run`, `lean_check` и `lean_session_*` также описывают ответы.
Например, `ffmpeg_run` возвращает `data.files` (имя → ссылка) и `data.playlist` (ссылка),
`lean_check` — `data.ok`, `data.proved`, `data.sorryCount` и сообщения проверки.
`code_run` — `data.value` (произвольный итог сценария), `data.output` и необязательный `data.build`.
При отсутствии `return` поле `value` может отсутствовать; `null` сохраняется как `null`.

Схемы опубликованы в `/openapi.json` и `/api/v1/openapi.json`; у chat endpoint та же схема
описывает непосредственно тело ответа. Обычный вызов и `async=1` используют одинаковую
проверку успешного результата; нарушение схемы возвращается как ошибка инструмента.
Не разбирайте `content[0].text` как JSON: полный результат находится в `data`.

## Большие загрузки в S3

`POST /api/v1/files/blob` с ключом и JSON `{"name":"video.mp4","size":524288000,"type":"video/mp4"}`
резервирует место и возвращает `id`, `upload_url` для PUT до 64 МиБ или `parts` для multipart.
Максимум объекта — до 5 ГиБ,
квота владельца — отдельно, по умолчанию 500 МиБ. Незавершённые загрузки резервируют эту же квоту;
одновременно их не больше пяти. Байты отправляются прямо в S3, через шлюз идёт только управление.

Каждая часть содержит `number`, `size`, `upload_url`, `headers`, `uploaded`; отправляйте ровно
указанный размер и возвращённые заголовки с `credentials: "omit"`. В браузере `Content-Length`
устанавливается автоматически по размеру `Blob`; вручную этот заголовок не задают.
Пустой подписанный `x-amz-copy-source` обязателен: его нельзя заменять на источник копирования.
Для curl пустой заголовок передаётся через `;` (с `:` curl удалит заголовок):

```sh
curl --request PUT "$UPLOAD_URL" --upload-file video.mp4 \
  -H 'content-type: application/octet-stream' -H 'x-amz-copy-source;'
```

Для multipart отправляйте отдельный файл части и заголовки из её билета.
PUT-ссылка живёт до пяти минут, загрузка и её квитанция — 24 часа.
В предел пяти входят только открытые записи: cancel и finish сразу освобождают слот.
Резерв квоты закрытой записи сохраняется до успешного удаления временных объектов уборкой
(`discarded`); отменённая загрузка продолжает резервировать заявленный размер.
После finish готовый блоб учитывается в квоте один раз; для завершённого multipart дополнительного
резерва нет, а для одиночного PUT остаётся резерв под возможный поздний PUT — `min(size, 64 МиБ)`.
Уборка выполняется раз в час и удаляет опоздавший PUT закрытой загрузки только после истечения
последней PUT-ссылки с запасом 10 минут. Само истечение ссылки не освобождает резерв квоты.
Общая длительность PUT не ограничена: непрерывный медленный PUT дольше срока ссылки + 10 минут
может оставить сироту `incoming/` до 24 часов, не более 64 МиБ на запись.

| Запрос с ключом | Действие |
|---|---|
| `GET /api/v1/files/blob/<id>` | свежие подписи, список уже принятых частей для докачки; готовая загрузка — результат |
| `POST /api/v1/files/blob/<id>/finish` | собрать multipart, проверить размер, SHA-256, тип по содержимому и квоту; вернуть `ref: "blob:sha256/<хеш>"` |
| `DELETE /api/v1/files/blob/<id>` | отменить и убрать временный объект/части; готовый блоб остаётся |
| `GET /api/v1/files/blob` | список своих готовых блобов |
| `GET /api/v1/files/blob/sha256/<хеш>` | метаданные и подписанный `url` для скачивания; `?inline=1` — показ безопасного типа |
| `DELETE /api/v1/files/blob/sha256/<хеш>` | снять свою ссылку, физическое удаление после срока без держателей |

После обрыва сохраните `id`, запросите статус и отправьте только части с `uploaded: false`.
После перезапуска шлюза состояние сохраняется. Если создание multipart оборвалось до выдачи
ссылок, отмените эту загрузку и создайте новую. `finish` повторяем; при ошибке квоты/типа
записи в индексе нет. При обрыве ожидания или HTTP `504` повторите
`POST /api/v1/files/blob/<id>/finish` с тем же `id`: обработка могла продолжиться после обрыва,
повтор вернёт сохранённый результат или завершит загрузку. Повтор finish ждёт завершения первого;
status/start владельца тоже ждут. Для 5 ГиБ finish может удерживать очередь владельца примерно
до двух часов. Загружать части заново не нужно.
Неизвестные форматы (в том числе CAD) указывайте как `application/octet-stream`;
заявленный конкретный MIME должен совпасть с распознанным, а тип, который сигнатурой не распознаётся
(например `text/markdown`), отклоняется уже при создании загрузки с тем же `415`.
Это распознавание сигнатур, не проверка исправности файла или антивирус. SVG, HTML, PDF
и неизвестные форматы скачиваются вложением; растровые картинки, MP4/WebM и распознанное аудио допускают inline. GET поддерживает `Range`.

В MCP `files_upload({name, size, type})` возвращает тот же билет без base64;
`files_upload({action:"status"|"finish"|"cancel", upload_id:"…"})` управляет загрузкой.
`blob:sha256/<хеш>` принимается в файловых аргументах инструментов с проверкой владельца,
при этом предел входа каждого инструмента сохраняется. `files_list` также показывает `blobs`,
`files_delete` принимает полную ссылку `blob:` в `id`. Публикация через `files_publish` остаётся
для `upload:`/`private:`. Статьи проектов используют ресурсы по путям и прежние права проекта;
публичные `blob:` в статьи не добавляются. Управление прямой загрузкой из MCP-вызова
с данными проекта закрыто; ресурсы проекта сохраняются прежним способом. Подписанные URL — секреты, не сохраняйте их в документах и журналах.


`ffmpeg_run` на CPU принимает свой `blob:sha256/<хеш>` до 5 ГиБ: шлюз передаёт недостающий вход потоком в дисковое хранилище узла, инструмент
читает его через read-only bind. Повторный запуск использует копию на узле. Удаление
последней ссылки владельца удаляет и копию; недоступный узел очищается при возвращении.
Для остальных ссылок ffmpeg сохраняется предел 32 МиБ, для остальных инструментов —
их прежние пределы. На CPU с настроенным CAS выход использует дисковый `/out` до 1024 МиБ
(часть занимает файловая система); шлюз сохраняет результат потоком в приватные файлы.
`files` и `playlist` содержат `private:`; `urls` — подписанные ссылки до 15 минут.
В `quota: {limitBytes, usedBytes, remainingBytes}` виден общий бюджет приватных результатов
владельца, включая этот HLS и результаты фоновых заданий. При чтении
приватного плейлиста ссылки на сегменты подписываются заново. Без CAS и на GPU выход — до 256 МиБ. Вызовы с данными проектов используют прежний
путь с пределом 256 МиБ и проверками версии/стирания проектного хранилища.
Синхронный срок ffmpeg — **300 с**. Даже 10 минут исходного видео 4K или тяжёлое кодирование
могут превысить его: используйте `?async=1` (MCP — фоновое задание, Code Mode — `.start`).
CPU batch допускает до **7200 с после старта**; ожидание очереди в этот срок не входит.
После завершения CAS-выход на узле доступен по lease не дольше часа; запись результата
сервера песочниц сохраняется как минимум на этот час, в том числе после первой выдачи шлюзу.
В пределах срока lease перезапуск шлюза может повторить получение выхода до сохранения
итогового результата задания. После истечения lease это восстановление не гарантируется.
Вложенный ffmpeg в фоновом `code_run` держит lease до сохранения внешнего задания
либо своего часового предела; несколько таких выходов делят бюджет CAS узла.
Если сборка не помещается в выделенную долю batch узла, совместимый интерактивный путь
сохраняет срок 300 с — смотрите срок задания в статусе.
Отказы называют причину: blob: больше предела (413, МиБ и точные байты), исчерпан бюджет
хранилища узла или место на томе (507, повторить позже), копия повреждена (422).
При 422 копия отбрасывается; повторите вызов, при повторении сообщите владельцу установки.
На общем GPU (NVENC) сохраняются прежний предел 32 МиБ и передача без монтирования хоста.
