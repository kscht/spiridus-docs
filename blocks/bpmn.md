# `bpmn` — процессы BPMN 2.0

Вариант без версии задаётся атрибутом строки ограждения `variant=<имя>` или аргументом MCP `variant`.
Допустимо: `auto`, `own`. По умолчанию — `own`.
Выбирается последняя не deprecated сборка варианта; точный `build` имеет приоритет.
Старую строку `build:` уберите, если переходите на `variant=`.

Схема бизнес-процесса в стандартной разметке BPMN 2.0 XML — той же, что у Camunda, bpmn.io и
большинства редакторов. По умолчанию работает самостоятельный SVG-просмотрщик
`bpmn-own-0.1.0`: сначала рисунок, по кнопке «Управлять схемой» — масштабирование,
темы и вложенные подпроцессы. Блок без `build=` использует эту сборку.

Для прежнего просмотра укажите `variant=auto`: это bpmn-js
со знаком «Powered by bpmn.io», который сохраняется по условиям его лицензии.
Обе сборки принимают тот же XML/YAML и передают шесть метрик сцены в `render_check`.

Процессы, пулы, дорожки и сообщения — **без координат**: bpmn-auto-layout **2.0.0-alpha.2** (bpmn.io contributors, MIT).

```bpmn
<?xml version="1.0" encoding="UTF-8"?>
<definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL" id="d1" targetNamespace="spiridus">
  <process id="p1" isExecutable="false">
    <startEvent id="s" name="Заявка получена"/>
    <sequenceFlow id="f1" sourceRef="s" targetRef="t1"/>
    <userTask id="t1" name="Проверить заявку"/>
    <sequenceFlow id="f2" sourceRef="t1" targetRef="g"/>
    <exclusiveGateway id="g"/>
    <sequenceFlow id="f3" sourceRef="g" targetRef="t2" name="всё заполнено"/>
    <sequenceFlow id="f4" sourceRef="g" targetRef="t3" name="не хватает"/>
    <serviceTask id="t2" name="Зарегистрировать"/>
    <userTask id="t3" name="Запросить недостающее"/>
    <sequenceFlow id="f5" sourceRef="t2" targetRef="e1"/>
    <sequenceFlow id="f6" sourceRef="t3" targetRef="e2"/>
    <endEvent id="e1" name="Готово"/>
    <endEvent id="e2" name="Возвращено"/>
  </process>
</definitions>
```

Дорожки связываются с узлами через `flowNodeRef`; пул — с процессом через `processRef`.
Координаты `BPMNShape`/`BPMNEdge` для них вычислять не нужно. Пулы и дорожки получают
мягкие оттенки по порядку модели; у секретаря цвет переопределён атрибутом:

```bpmn
<definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL" xmlns:color="http://www.omg.org/spec/BPMN/non-normative/color/1.0"
  id="Defs_lanes" targetNamespace="spiridus">
  <collaboration id="Collaboration_lanes">
    <participant id="Pool" name="Заявка" processRef="Process"/>
  </collaboration>
  <process id="Process" isExecutable="false">
    <laneSet id="Lanes">
      <lane id="Applicant" name="Заявитель"><flowNodeRef>Start</flowNodeRef><flowNodeRef>Submit</flowNodeRef></lane>
      <lane id="Clerk" name="Секретарь" color:background-color="#ffe2bd"><flowNodeRef>Check</flowNodeRef><flowNodeRef>Register</flowNodeRef></lane>
      <lane id="Manager" name="Руководитель"><flowNodeRef>Approve</flowNodeRef><flowNodeRef>End</flowNodeRef></lane>
    </laneSet>
    <startEvent id="Start" name="Начало"/>
    <userTask id="Submit" name="Подать заявку"/>
    <userTask id="Check" name="Проверить заявку"/>
    <serviceTask id="Register" name="Учесть заявку"/>
    <userTask id="Approve" name="Согласовать"/>
    <endEvent id="End" name="Готово"/>
    <sequenceFlow id="F1" sourceRef="Start" targetRef="Submit"/>
    <sequenceFlow id="F2" sourceRef="Submit" targetRef="Check"/>
    <sequenceFlow id="F3" sourceRef="Check" targetRef="Register"/>
    <sequenceFlow id="F4" sourceRef="Register" targetRef="Approve"/>
    <sequenceFlow id="F5" sourceRef="Approve" targetRef="End"/>
  </process>
</definitions>
```

Для нескольких пулов объявите `collaboration` с `participant` для каждого процесса и
`messageFlow` с `sourceRef`/`targetRef` между их узлами (или самими участниками).
`sequenceFlow` связывает узлы только внутри одного процесса; между пулами идут сообщения.

Готовая схема `bpmndi:BPMNDiagram` **главнее авто-раскладки**: библиотека не рассчитывает
DI повторно. Собственный просмотрщик использует её как исходную точку, увеличивает
задачи под текст и разносит подписи/линии; исходный XML не меняется. Для предпочтительных
сторон подписей, порядка и маршрутов используйте `layout:` ниже. У явной сборки bpmn-js
готовые координаты сохраняются. В собственной сборке при `di=adjust` ширина задачи — не меньше 120 px,
событие обычно 36×36, шлюз 50×50.

Предупреждения раскладки показываются под рисунком и входят в замечания `render_check`.
При `LayoutError` простой процесс пробуется прежней 1.3.0 с явным предупреждением.
Для пулов, дорожек и сообщений запасного показа нет: 1.3.0 их теряет; нужна готовая DI-схема.
Прежний вид простых процессов можно закрепить явно: ` ```bpmn build=bpmn-auto-1.3.0 `.
Эта сборка сохранена для совместимости и по-прежнему не раскладывает пулы и дорожки.

**Палитра включена по умолчанию**: задачи, пулы, дорожки и события получают
сдержанные оттенки. `colors=auto` (синоним `on`) включает её явно; `colors=off`
оставляет только цвета модели. Модельный цвет главнее палитры. Подписи получают
контрастный цвет по фактическому фону, линии — контрастную подложку при необходимости.
Холст по умолчанию светлый; `canvas=dark` включает тёмный, кнопка «Тема» переключает его.
У явной сборки bpmn-js палитра применяется при авто-раскладке, холст остаётся светлым.

**Свой цвет без координат** задавайте прямо на `lane`, `participant`, задачах, шлюзах,
событиях и связях. Стандарт «BPMN in Color»: `color:background-color="#dbe9ff"`,
`color:border-color="#234567"`, с объявлением
`xmlns:color="http://www.omg.org/spec/BPMN/non-normative/color/1.0"`.
Расширение bpmn.io: `bioc:fill="#dbe9ff"`, `bioc:stroke="#234567"`, с объявлением
`xmlns:bioc="http://bpmn.io/schema/bpmn/biocolor/1.0"`. Префиксы могут быть другими.
После раскладки значения переносятся на соответствующие `BPMNShape`/`BPMNEdge`.
Свой фон и обводка независимо заменяют палитру и работают при `colors=off`.
Если оба способа задают одно свойство, допустимый стандартный `color:` главнее `bioc:`.
Допустимы только `#rgb` и `#rrggbb` (регистр букв любой). Имена цветов, `url(...)`,
прозрачность и другие записи игнорируются с предупреждением в рисунке и `render_check`.
Проверьте `label-contrast`. В явной сборке bpmn-js цвет обводки используется и для текста: на светлом холсте выбирайте тёмную обводку.

У готовой DI цвета задаются на самих `BPMNShape`/`BPMNEdge` теми же атрибутами.
В собственной сборке палитра применяется и к готовой DI; модельный цвет приоритетен и сохраняется при `colors=off`. В явной сборке bpmn-js палитра к готовой DI не применяется.
Сборка `build=bpmn-auto-1.3.0` сохраняет прежний показ без палитры и переноса цветов.

Несколько схем в одном файле (`bpmndi:BPMNDiagram` с разными `id`) — какую показать, первой
строкой: `<!-- diagram: BPMNDiagram_2 -->`. Без неё — первая.

## Вложенные схемы подпроцессов

Содержимое `subProcess` можно написать **в том же блоке**: авто-раскладка создаст
отдельную вложенную схему. На общей схеме подпроцесс показан свёрнутым, с плюсом;
нажмите сам подпроцесс, чтобы открыть содержимое. Кнопка «Назад» возвращает на
родительский уровень. В явной сборке bpmn-js используйте стрелку и путь над схемой. Переходы сразу обновляют рисунок и размер блока, без прокрутки;
они работают и в статье, и в полноэкранном просмотре, сохраняя тот же живой фрейм.
Можно вкладывать подпроцессы друг в друга.

```bpmn
<definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL" id="Nested" targetNamespace="spiridus">
  <process id="Order" name="Заявка" isExecutable="false">
    <startEvent id="Begin"/>
    <subProcess id="Review" name="Проверить заявку">
      <startEvent id="ReviewBegin"/>
      <task id="Check" name="Сверить данные"/>
      <endEvent id="ReviewEnd"/>
      <sequenceFlow id="R1" sourceRef="ReviewBegin" targetRef="Check"/>
      <sequenceFlow id="R2" sourceRef="Check" targetRef="ReviewEnd"/>
    </subProcess>
    <endEvent id="Finish"/>
    <sequenceFlow id="O1" sourceRef="Begin" targetRef="Review"/>
    <sequenceFlow id="O2" sourceRef="Review" targetRef="Finish"/>
  </process>
</definitions>
```

Для готовой DI нужны `BPMNShape` с `isExpanded="false"` в родительской схеме и
отдельный `BPMNDiagram`/`BPMNPlane` с `bpmnElement="Review"` для содержимого.
Готовая DI служит исходной точкой. Пустой `subProcess` без отдельной плоскости не имеет
вложенного рисунка; подробности можно по-прежнему дать отдельным блоком ниже.
Если подробности относятся к отдельному процессу, используйте `callActivity` с
`calledElement`, а не пустой `subProcess`. Для перехода по нажатию вызываемый `process`
и его `BPMNDiagram` должны находиться в том же XML-блоке: соседний Markdown-блок
не входит в модель этого просмотрщика.

`render_check` рисует и проверяет все вложенные схемы блока теми же правилами,
что и верхнюю: возвратные связи и подписи проверяются внутри своей плоскости.
Замечание содержит название вложенной схемы, её `diagram` и `element` с id элемента.
Нечитаемые подписи (`label-crossed`, `label-overlap` и другие) исправляйте по рецептам
ниже; полноэкранный просмотр не устраняет пересечения. Для проверки переходов сначала нажмите «Управлять схемой», затем
добавьте `interact` со строкой ограждения блока: `click: '[data-role="shape"][data-element-id="Review"]'`,
возврат — `click: 'button[aria-label="Вернуться к родительской схеме"]'`.
Повторите в полном экране. В явной сборке bpmn-js переход —
`'[data-container-id="Review"] .bjs-drilldown'`, возврат — `'.bjs-breadcrumbs a'`.
CSS-селектор шага ищется также внутри фрейма.

Ограничения: не больше 256 КБ; ссылки, картинки и внешние файлы в разметке не работают;
вход — XML либо стандартный YAML с полями `xml:` и `layout:`. Ошибка разбора показывается под исходником с
сообщением просмотрщика.

Ловушки:
- `incoming` и `outgoing` у узлов писать не нужно: достаточно `sourceRef` и `targetRef` у
  `sequenceFlow`, недостающие ссылки фрейм дописывает сам перед авто-раскладкой.
- Авто-раскладка не проверяет процесс: без стартового события или с разрывами в потоке она
  просто расставит узлы столбиком. Если схема вышла вертикальной — ищите разрыв в `sequenceFlow`.
- Пространство имён по умолчанию — MODEL; для схемы нужны `xmlns:bpmndi`, `xmlns:dc`, `xmlns:di`.
- Подписи на русском — обычным текстом в `name`; кавычки внутри — `&quot;`.
- Длинные названия задач переносятся внутри фигуры по словам; для осмысленного переноса
  можно написать `name="Проверить&#10;заявку"`. Сократите подписи до двух-трёх коротких строк.
- На ширинах 760/390 px схема целиком вписывается в колонку. Если текст уменьшенного
  превью мелок, `render_check` сообщает `diagram-preview` и предлагает «⤢» → «100 %».
  «Вместить» показывает общий вид, «100 %» возвращает натуральный размер с прокруткой.
  Для короткого обзора сворачивайте подпроцессы и уменьшайте число шагов на одном уровне.
  Полный экран не устраняет пересечения или мелкий текст при 100 %.

## Подсказки `layout:` без координат

Внутри блока `bpmn` можно вместо одного XML написать **стандартный YAML**. XML находится
в многострочной строке `xml: |`, подсказки — в объекте `layout:`. Никаких директив вне блока,
нового синтаксиса XML и редактора BPMN для этого не нужно:

```bpmn
xml: |
  <definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL" id="D" targetNamespace="spiridus">
    <process id="P" isExecutable="false">
      <startEvent id="S" name="Начало"/>
      <task id="T" name="Проверить заявку"/>
      <endEvent id="E" name="Готово"/>
      <sequenceFlow id="F1" sourceRef="S" targetRef="T" name="Проверка"/>
      <sequenceFlow id="F2" sourceRef="T" targetRef="E"/>
    </process>
  </definitions>
layout:
  labels:
    S: {side: top, offset: normal}
    F1: {side: top, offset: normal, shift: center}
  elements:
    - [S, T, E]
  edges:
    F2: {exit: right, enter: left}
```

Все ключи в `labels` и `edges`, все значения в списках — **id BPMN**, а не текст подписи.
Одинаковые названия допустимы. Обычный XML и YAML без `layout` обрабатываются как раньше;
палитра и `colors=off` работают и с подсказками. Подсказки превращаются в стандартную BPMN DI
**до загрузки просмотрщика**, одинаково для живой схемы и SVG.

| Поле | Значения и действие |
|---|---|
| `labels.<id>.side` | `top`, `bottom`, `left`, `right` — сторона внешней подписи события, шлюза, sequenceFlow, messageFlow или association |
| `labels.<id>.offset` | `small`, `normal` (по умолчанию), `large` — зазор от фигуры/отрезка |
| `labels.<id>.shift` | `before`, `center` (по умолчанию), `after` — сместить вдоль стороны до/после её середины; у линии выбирается самый длинный отрезок |
| `lanes` | Например `[Manager, Clerk, Applicant]`: порядок сверху вниз соседних дорожек одного `laneSet`, в том числе вложенного. Перечисленные идут первыми, остальные сохраняют свой порядок |
| `elements` | Список списков, например `[[Check, Register], [Approve, End]]`: каждый список задаёт порядок слева направо внутри одной дорожки или процесса |
| `edges.<id>.exit`, `.enter` | `top`, `bottom`, `left`, `right`: сторона выхода и входа линии |
| `edges.<id>.around` | Например `{id: Register, side: top}`: провести линию через свободное место над указанной фигурой; остальные фигуры обходятся автоматически |

У `labels` обязательно поле `side`; `offset` и `shift` необязательны. В `edges` достаточно
одного из `exit`, `enter`, `around`; пропущенные стороны выбираются автоматически. Числовые
координаты и смещения не принимаются. Подписи внутри задач, пулов и дорожек остаются внутри
фигур: `labels` для них выдаёт `layout-type`; сокращайте `name` и добавляйте переносы `&#10;`.
Порядок одного id нельзя задать дважды; списки из разных дорожек/процессов не объединяются.
Неперечисленные элементы сохраняют место, поэтому частичный порядок может оставить пересечение:
включите конфликтующие id в один список и повторите проверку.

Граничное событие (`boundaryEvent` с `attachedToRef`) переносится вместе с задачей-хозяином,
сохраняя относительное положение и подпись; его линии перестраиваются. Отдельно ставить его
в `elements` нельзя. Наложение такого события на своего хозяина допустимо, как и выход
части кружка за рамку дорожки хозяина; пересечение с другой фигурой остаётся проблемой.
У `dataInputAssociation`/`dataOutputAssociation` ссылки читаются из дочерних `sourceRef`/
`targetRef`; конец на `dataInput`/`dataOutput` относится к отображаемому владельцу
`ioSpecification`. У нескольких `sourceRef` одна DI-линия показывает первый источник.

Подсказки можно применять и к готовой DI: она служит начальной сценой; `layout` меняет её явно.
Исходный XML готовой DI сохраняется побайтно; собственный просмотрщик может
поправить конечную геометрию под текст. Выбор схемы по `<!-- diagram: Id -->` находится
в начале строки `xml`, как и в обычном XML. Старая сборка `build=bpmn-auto-1.3.0` YAML не понимает.

Для каждого блока `bpmn` фрейм и проверка нотации проверяют сцену: XML, YAML без
`layout` и с ним (включая `layout: {}`). Общий измеритель #1059 используется в обеих
сборках: у bpmn-js — окончательная DI, у собственной — конечные фигуры/линии после
размещения и фактические рамки SVG-текста. Программа проверки нотации измеряет DI
до просмотра; её результаты могут отличаться от исправленной сцены SVG. Коды проблем:
`layout-label-edge`, `layout-label-overlap`, `layout-label-node`, `layout-node-overlap`,
`layout-edge-node`, `layout-edge-crossed`, `layout-edge-overlap`, `layout-label-tight`, `layout-container-tight`. Каждая содержит один или два id
(например `BPMN layout-label-edge [S, F1]`) и поле подсказки, которое стоит изменить.
`layout-id`/`layout-type`/`layout-order` сообщают об ошибках ссылок и ограничений; при них
все подсказки блока отклоняются, начальная DI сохраняется. Неизвестные поля и неверный YAML —
ошибка блока. Общая проверка настоящего текста SVG дополнительно находит мелкие подписи,
недостаточный контраст и пересечения текста внутри задач.

Цикл исправления конечный: вызовите `render_check`, возьмите id из замечания, измените одну
подсказку и повторите с новым содержимым. Если результат повторился, меняйте другую сторону,
обход или порядок. Просмотрщик выполняет ограниченный поиск; неустранимые проблемы
остаются в замечаниях и метриках.
Предел применения подсказок — 200 фигур, 400 линий, 100 000 шагов поиска маршрута за один блок; превышение даёт
`layout-budget`. Если маршрут не найден (`layout-route`), сохранён прежний путь и выдано
замечание; если при перестановке не удалось перестроить хотя бы одну линию, вся перестановка
отменяется и сохраняется начальная DI. Ложного сообщения об успешном исправлении нет. После первых 100 геометрических
проблем выводится `layout-problem-budget` с полным числом; сначала исправьте показанные.
Измерение сцены выполняется полностью и при отклонении подсказок, по сохранённой DI.

`render_check` возвращает `sceneMetrics: [{line, lang, at, metrics}]`: `line` — строка
ограждения, `at` — ширины проверки. В полном `meta.json` это `widths[ширина].blocks[].sceneMetrics`.
В собственной сборке это сумма конечных сцен всех плоскостей, включая свёрнутые
подпроцессы до их открытия. `sceneMetricsByView` рядом содержит те же шесть счётчиков
отдельно по id каждой плоскости; сумма совпадает с `sceneMetrics`. SVG, серверный
результат и живой просмотр используют одну сводку. Ноль означает отсутствие
обнаруженных геометрических дефектов после размещения, а не отсутствие вложенных схем.
Программа проверки нотации возвращает в `meta.json`
`sceneMetrics: [{line, lang, metrics}]`, независимо от ограничения замечаний. Счётчики:

| Поле `metrics` | Что считается |
| --- | --- |
| `edgeCrossings` | Каждая отдельная точка пересечения каждой пары линий; несколько точек пары считаются отдельно, дубли в waypoint убираются |
| `edgeOverlaps` | Каждый отдельный участок наложения или тесного параллельного хода пары линий |
| `edgesThroughNodes` | Число разных линий, проходящих через чужие фигуры |
| `labelsIntersecting` | Число разных подписей (включая заголовки контейнеров), чьи рамки пересекают подпись, фигуру или линию |
| `labelsTight` | Число разных подписей (включая заголовки контейнеров) с касанием или зазором меньше 3 DI до подписи, фигуры или линии |
| `nodesOverlapping` | Число разных фигур, участвующих в наложении |
| `containerTight` | Число разных пар «элемент — свой пул/дорожка», где фигура или её внешняя подпись ближе `containerGap` к границе либо за ней |

Одна подпись может войти в обе метрики при разных соседях. Метрики не выводятся из первых
100 замечаний. Для приёмки «ноль по всем» проверяйте наличие всех семи полей и их нулевые
значения; отсутствие метрик означает отсутствие результата измерения.

Пороги заданы константами в единицах DI, независимо от масштаба: параллельные линии с
зазором **меньше 4** и общей проекцией **длиннее 8** считаются наложением; при нулевом
зазоре действует тот же порог длины. 4 DI отделяет сливающиеся обводки, 8 DI отсекает
короткие касания у поворота; равенство порогам не считается проблемой. Промежуточные
коллинеарные и повторные waypoint на результат не влияют. Допуск арифметики — `1e-7`.
Встреча двух концов разрешена. У общей source/target-фигуры разрешён подход/выход длиной
20 DI вдоль полилинии, включая изгибы (длина порта нашего роутера): оба конца должны
лежать на рамке этой фигуры и
находиться ближе 4 DI друг к другу. Это допускает короткое слияние перед шлюзом.
Остаток общего маршрута за пределами 20 DI проверяется с порогом длины 8 DI;
одинаковый targetRef сам по себе длинное совпадение не скрывает.
Контейнеры (пулы, дорожки, раскрытые подпроцессы) не считаются препятствиями;
касание границы фигуры и штатное наложение граничного события на хозяина разрешены.

Общий измеритель использует прямоугольные рамки фигур; собственная сборка передаёт
ему фактические рамки текста, включая повёрнутые заголовки пулов/дорожек. Точная форма
ромбов, значки и контраст дополнительно проверяются общим анализатором SVG. Изменение порядка перестраивает маршруты, изменение одной
подписи сохраняет положения фигур и линии. Результат повторяем при одинаковом входе.

### Зазор до границы своего контейнера

`layout-container-tight` — **предупреждение**, когда фигура или её внешняя подпись
ближе 12 DI к любой внешней границе своего пула или дорожки либо выходит за неё.
Ровно 12 DI допустимо. Порог можно изменить стандартным YAML: `layout: {containerGap: 16}`
(число от 0 до 10000 DI). Эта настройка сама по себе не перемещает элементы и не меняет
готовую XML/DI. Нулевой порог оставляет проверку выхода за границу.

В сообщении есть код, id элемента и контейнера, сторона, расстояние в DI и совет,
на сколько сдвинуть фигуру/подпись внутрь или расширить контейнер наружу. Отрицательное
расстояние означает выход за рамку. Например, для конечного события в 4 DI от правой
границы совет — сдвинуть влево или расширить пул вправо минимум на 8 DI.
После исправления повторите `render_check`: сдвиг может затронуть другие элементы.

Принадлежность определяется моделью BPMN (`processRef`, `flowNodeRef`, предки подпроцесса,
хозяин граничного события), поэтому выход за рамку не скрывает проблему. Чужой геометрически
близкий пул не назначается владельцем; межпуловая подпись `messageFlow` не получает пул
по положению. Сами дорожки, пулы и их внутренние заголовки в эту метрику не входят.
Одна пара считается один раз, даже если тесны фигура, подпись и несколько сторон;
для каждой стороны и части выводится отдельное предупреждение. Свой пул и своя дорожка
считаются отдельными парами.

В обеих сборках проверяется конечная сцена и фактический внешний текст, включая подписи
без `BPMNLabel`; линтер без браузера проверяет рамки DI. В `bpmn-own` новый счётчик сам
по себе не запускает перестройку сетки. Предупреждение не превращается в ошибку; метрики
передаются отдельно, даже если замечания ограничены или скрыты через `lint-ignore`.

## Проверка модели BPMN

`render_check` и `lint_check` проверяют модель через bpmnlint. Сообщения включённых правил
даны по-русски, содержат id элемента и совет по исправлению. Замечания линтера имеют
`kind: lint` и сами по себе не меняют `clean`; геометрию рисунка проверяйте отдельно.

- `gateway-branch-limit`: предупреждение, если у шлюза **больше 5 исходящих** или
  **больше 5 входящих** переходов `sequenceFlow`. Входы и выходы считаются отдельно,
  в том числе у шлюзов внутри подпроцесса. Разбейте выбор на два ромба, вынесите часть
  процесса в подпроцесс или представьте условия таблицей решений. Один `layout` не
  упрощает модель с множеством веток.
- `label-required`: ромб-развилка может быть без `name`, если подписаны **все исходящие
  ветки**. Пустая или состоящая из пробелов подпись ветки не считается подписью.
  Для задач, событий и остальных элементов требования подписей сохраняются.
- `empty-collapsed-subprocess`: у пустого свёрнутого `subProcess`, подробности которого
  описаны отдельной схемой, используйте `callActivity` с `calledElement`, указывающим на
  вызываемый процесс. Вместо двух сообщений `start-event-required`/`end-event-required`
  будет один совет. Раскрытый или непустой подпроцесс по-прежнему должен содержать
  начальное и конечное события; для событийного и ad hoc подпроцесса действуют их правила.

Порог числа веток настраивается для всего блока в YAML рядом с `xml` и `layout`:

```yaml
xml: |
  <definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL" id="D" targetNamespace="spiridus">
    <!-- процесс BPMN -->
  </definitions>
lint:
  maxGatewayBranches: 7
```

`maxGatewayBranches` — положительное целое число, по умолчанию 5. Ровно N веток
разрешены. Настройка не меняет рисунок; обычный XML без YAML использует порог 5.
`lint-ignore=gateway-branch-limit` в строке блока подавляет только это правило;
`lint=off` отключает проверку линтером всего блока.

## Как чинить замечания `render_check`

`render_check` смотрит внутрь рисунка: `label-crossed` — линия через подпись, `label-tight` — линия касается подписи, `label-overlap` — подписи налезают, `label-outside` — подпись шире своей фигуры, `label-small` — подписи мельче 9 точек при 100 % в полном экране. Уменьшение превью (`too-small`/`label-small`) сообщается как `diagram-preview`, `severity:info`; пересечения подписей проверяются по-прежнему. В замечании — текст подписи, а в ответе — вырез места (`label-<строка>-<n>.png`).

Замечание `label-crossed` называет препятствие и его id: границу дорожки, край пула,
граничное событие, рамку или маркер `callActivity`, конкретную линию потока. Это элементы
фактического SVG, поэтому две части одного значка больше не выдаются за «2 линии».

Для внешней подписи в готовой DI `hint` предлагает сдвиг в единицах DI и новые `x`/`y`
`BPMNLabel/dc:Bounds`. Кандидат проверяется по рамкам фактического текста, фигурам, границам
контейнеров и маршрутам той же сцены. Принадлежность к пулу/дорожке берётся из модели,
даже когда подпись уже за рамкой; кандидат выдерживает заданный `containerGap`. Поиск ограничен 120 DI по каждой оси с шагом 4; при отсутствии места
сообщает об этом. Это совет: исходник и координаты не изменяются; после правки нужен новый
`render_check`. Шесть метрик #1059 сохраняют прежний смысл; `containerTight` дополняет их.

Внешние подписи событий, шлюзов, объектов/хранилищ данных и линий проверяются одинаково.
Если рамка внешней подписи уже текста, подсказка сообщает «нужна ширина не меньше N DI».
Ширина измеряется шрифтом текущей сборки для строки без дополнительного переноса; явные
`&#10;` сохраняются. Увеличьте `width`, затем снова проверьте расположение: более широкий текст
может потребовать нового места. Переносы сами по себе не считаются ошибкой.

У `callActivity` 100×60 с двумя строками в bpmn-js нижняя строка может попадать на рамку
маркера «+». Это реальное пересечение: задайте высоту от 70 DI; для более длинного текста
может понадобиться больше. bpmn-own уже увеличивает тесные фигуры автоматически, сохраняя
исходную DI. Для обеих сборок проверяются получившиеся SVG, а не только размеры входа.

- `layout-edge-overlap` — линии сливаются или идут впритык: по id выберите для одной `layout.edges.<id>: {exit: bottom, enter: top}`, при необходимости добавьте `around` существующей фигуры или измените `layout.elements`. Для готовой DI можно развести waypoint в редакторе. Короткое штатное слияние у шлюза разрешено; длинный общий маршрут нужно разделить.
- `layout-label-tight` — увеличьте `layout.labels.<id>.offset` или измените `side`/`shift`.
- `layout-label-edge` / `layout-label-overlap` — измените `layout.labels.<id>`: сначала `side`, затем `offset`/`shift`; у линии можно изменить `layout.edges.<id>`.
- `label-crossed` у подписи сообщения или связи — используйте `layout.labels.<id>: {side: top, offset: normal}`; для точной DI задайте место: `<bpmndi:BPMNLabel><dc:Bounds x y width height/></bpmndi:BPMNLabel>` внутри `BPMNEdge`; для сообщения между пулами — в промежуток между ними (не на границу пула и не на дорожку), сбоку от линии на 6 точек.
- `label-crossed` у подписи события или шлюза — `BPMNLabel` над фигурой, если связь входит снизу (и наоборот); у шлюза в авто-раскладке подпись под ромбом всегда пересекает ветвь вниз — уберите `name` у шлюза, а вопрос пишите в подписях ветвей (`name` у `sequenceFlow`).
- `label-crossed` на названии задачи — значок типа (`userTask`, `serviceTask`) в углу лёг на перенесённый текст: сократите название до двух строк или используйте `task` без значка.
- `label-tight` у подписи события — `layout.labels.<id>: {side: bottom, offset: normal}` или отступите на 8 точек от кружка (`dc:Bounds` с `y = низ кружка + 8`).
- `diagram-preview` (`too-small`/`label-small`) — мелко только на уменьшенном превью: это информация, а не замечание; «⤢ Открыть» → «100 %» позволяет читать схему в натуральном размере. Подпроцессы, меньше столбцов и переносы коротких подписей через `&#10;` помогают общему обзору.
- `label-small` при 100 % — текст мелок и в полном экране: увеличьте размер подписей в DI или исправьте исходную схему. Открытие полного экрана само по себе такое замечание не снимает.

## Просмотр на телефоне

На телефоне широкая схема сначала целиком вписывается в колонку. «Управлять схемой»
включает масштабирование, перетаскивание и вложенную навигацию. «Вместить» показывает
всю схему, «100 %» возвращает натуральный размер. Полный экран закрывается кнопкой,
Esc или «назад» браузера. С клавиатуры: Tab выбирает управление, стрелки сдвигают
схему, + и − меняют масштаб. В явной сборке bpmn-js «⤢ Открыть» разворачивает превью.

## SVG и управление схемой

`variant=own` выбирает собственный просмотрщик без закрепления версии; без `build=` работает
тот же самостоятельный SVG-просмотрщик. Сначала показывается SVG;
кнопка «Управлять схемой» или полный экран загружают масштабирование, темы и переходы
во вложенные подпроцессы. Блоки вне экрана загружаются при прокрутке.

Шрифт — системный, 14 px. Широкая схема сначала показывается целиком как превью;
для чтения подробностей доступны «⤢» и «100 %». В интерактивном просмотре новая
вложенная схема тоже вписывается сразу; «100 %» включает натуральный размер с прокруткой.
DI служит исходной точкой: размеры задач растут под текст, подписи получают свободное
место с зазором 12 px, линии обходят подписи. Исходный XML не изменяется.
Подсказки `layout:` применяются и в этой сборке; сторона подписи предпочтительна,
при конфликте выбирается ближайшее свободное место.

`colors=auto` (синоним `on`) включает сдержанную палитру. Цвета из модели имеют
приоритет; `colors=off` оставляет только цвета модели. `canvas=dark` выбирает тёмный
холст собственной сборки, `canvas=light` — светлый (по умолчанию). В интерактивном
просмотре холст можно переключить кнопкой «Тема». Кнопка «SVG» сохраняет активную
схему после подтверждения «Сохранить SVG» в окне документа.

Предварительно подготовленный результат можно указать начальными строками **внутри**
блока перед XML или YAML:

````markdown
```bpmn
result: media/process.json
size: 1408x844
<definitions ...>...</definitions>
```
````

`result:` — ссылка на подготовленный JSON в ресурсах проекта или `artifact:…`;
`size:` — его естественные размеры, резервирующие место до загрузки. Готовый SVG
показывается без загрузки просмотрщика и раскладки. Результат связан хешем с точным
текстом XML/YAML, подсказками, цветами, холстом и версией сборки: после их изменения
нужна повторная подготовка. Чужой или устаревший результат даёт ошибку блока.
Без `result:` SVG готовится в браузере; готовая DI повторно не вычисляется при включении
управления схемой.

### Готовая DI: точный показ и изменения просмотрщика

У собственной сборки атрибут блока `di=exact` включает режим «как в разметке»:
координаты и размеры фигур, все waypoints и заданные рамки внешних `BPMNLabel`
сохраняются. Задачи не расширяются, линии не перестраиваются, подписи не разводятся.
Стиль остаётся собственным; текст переносится в заданной области, а теснота и
пересечения остаются видны проверке. Для внешней подписи без BPMNLabel берётся одно
обычное место около элемента без поиска свободной стороны. Нужна готовая
`BPMNDiagram`: без неё `di=exact` сообщает ошибку вместо авто-раскладки. Подсказки
перестановки `layout` в этом режиме не применяются; `containerGap` остаётся порогом проверки.

Без атрибута (или при `di=adjust`) действует обычное размещение: DI — исходная точка.
Если готовая DI изменена, `render_check` возвращает **предупреждение** с
`code: di-adjusted`, id элемента, изменениями `x/y/width/height`, рамки подписи или
маршрута в DI и советом поправить DI либо выбрать `di=exact`. Для маршрута сообщаются
число waypoints до/после и наибольшее расстояние waypoint до ближайшего исходного/нового;
точные массивы координат доступны в `adjustments` результата собственной сборки.
Неизменённая готовая DI и схема без исходной DI такого предупреждения не получают.

`sourceMetrics` содержит полные счётчики **исходной готовой DI до layout и размещения**,
а `sceneMetrics` — нарисованной сцены. В полном отчёте оба поля лежат в блоке;
в кратком ответе `render_check` — списки `{line, lang, at, metrics}`.
`sourceMetricsByView` и `sceneMetricsByView` содержат значения по плоскостям, сводные
метрики равны их суммам. При отсутствии готовой DI `sourceMetrics` не возвращается.
Нулевые конечные счётчики не означают, что исходная DI была чистой: проверяйте обе сводки.
Например, задачи a (100,100,100×80) и b (130,120,100×80), а также пересекающиеся
f1 (150,180)→(450,80) и f2 (180,120)→(450,300) дают
`sourceMetrics.nodesOverlapping >= 1` и `sourceMetrics.edgeCrossings >= 1`
даже после автоматического исправления. Режим и обе сводки входят в ключ/контракт
готового снимка и одинаково передаются в обычном просмотре и проверке.
