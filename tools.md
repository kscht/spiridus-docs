# Инструменты

Что умеет Spiridus — по инструментам. Они одни и те же в [MCP](mcp.md) и [REST API](api.md); все
аргументы с типами и пределами — [arguments.md](arguments.md) (машинно — `GET /api/v1/tools`,
`openapi.json`), здесь — зачем он и что получится.

У каждого инструмента есть необязательное поле `task` — 2–3 предложения о том, какую просьбу
пользователя модель сейчас выполняет. Оно ни на что не влияет в ответе, но помогает нам понять, где
проверки ошибаются ([data.md](data.md)).

Обычный порядок — у модели и у человека, который зовёт инструменты сам: узнать, какие блоки есть и как
их писать → написать документ → проверить → поправить замечания → проверить снова → поделиться
ссылкой (`document_share`). Блоки, которые рисуются на сервере (PlantUML, схемы ПЛИС, модели…),
сначала отправляются на отрисовку, а в документ вставляется ссылка на готовый результат.

## Справка и примеры

| Инструмент | Зачем | Что в ответе |
|---|---|---|
| `render_blocks` | узнать, какие наглядные блоки есть: диаграммы, схемы, формулы, химия, ноты, 3D, карты… | список языков блоков с короткими пояснениями |
| `render_block_docs` | как писать блок нужного языка | справка: синтаксис, ограничения, рабочий пример |
| `render_examples` | найти готовый образец под задачу («диаграмма последовательности с ветвлением», «карта с раскраской областей») | 2–3 блока, которые проходят проверку, и ссылки на страницы примеров |
| `render_recipes` | как починить конкретное замечание проверки в конкретной библиотеке | проверенные приёмы — и отмеченные как не помогающие |
| `render_icons` | иконки для схем Mermaid и D2: сетевые устройства, ИТ, логотипы | имена иконок и как их вставить |
| `render_shapes` | контуры и карты для диаграмм ECharts | названия карт и их частей, автор и лицензия |
| `render_media` | картинки, которые можно вставить в документ | список с автором, лицензией и строкой для вставки |

## Проверка

| Инструмент | Зачем | Что в ответе |
|---|---|---|
| `render_check` | отрисовать документ так, как его увидит читатель — на компьютере и на телефоне, — и найти, что не так | `clean` — чисто или нет; список замечаний со строкой документа: блок не собрался, подписи налезают друг на друга, рисунок шире колонки или слишком мелкий, формула с ошибкой, опечатки и стиль текста ([russian.md](russian.md)); по желанию — снимки блоков и страницы |
| `lint_check` | быстро проверить линтерами один блок кода (`code` и `lang`) или весь документ — без отрисовки; `text: true` — и русский текст | `clean`, замечания `{ line, tool, rule, text, hint }`; у блока строки — по его коду |

Документ передаётся целиком, одной строкой, в поле `markdown`. Можно проверить и поведение живых блоков:
нажать кнопку, щёлкнуть по входу схемы — и посмотреть, что изменилось.

## Рисование на сервере

Эти блоки собираются на сервере, потому что для них нужна полноценная программа. Ответ — рисунок или
результат расчёта и готовая строка, которую вставляют в блок документа. Одинаковый запрос второй раз
отвечает сразу, из готового: `"cached": true`, без очереди и лимита ([api.md](api.md#кеш-результатов)).

| Инструмент | Зачем | Что в ответе |
|---|---|---|
| `plantuml_run` | схемы PlantUML: UML, C4, сети, mind map, диаграммы Ганта | схема SVG, предупреждения или ошибка со строкой |
| `structurizr_run` | архитектура по модели C4 на языке Structurizr DSL | каждый вид модели — рисунком, ошибки со строкой |
| `quantum_run` | квантовые схемы OpenQASM | схема, вероятности исходов, сферы Блоха, ZX-диаграмма и её упрощение |
| `hdl_synth` | Verilog, SystemVerilog, VHDL: проверка и синтез | схема RTL, живая схема для щелчков по входам, ресурсы ПЛИС и предельная частота |
| `hdl_sim` | симуляция тестбенча | осциллограммы для блока и вывод тестбенча |
| `modelica_run` | расчёт модели Modelica: механика, электрика, тепло; `set` — другие значения параметров | графики переменных, у механизмов — анимация |
| `cad_run` | 3D-модель по сценарию FreeCAD на Python | модель STL и STEP, объём, площадь, габариты; модель от таблицы параметров (ячейки с псевдонимами) — `params` и блок ```` ```freecad ```` с полями для читателя |
| `cad_recompute` | пересчитать готовую модель FreeCAD (FCStd) с другими значениями параметров, без сценария | то же, что у `cad_run` |
| `blender_run` | сцена Blender: кадр, конвертация моделей | картинка или файлы моделей; меши в сцене — `model.stl` и готовый блок ```` ```stl ```` (`max_triangles` огрубляет сетку), `scene.blend` — сцена целиком |
| `qet_run`, `qet_symbols` | электрические схемы и символы QElectroTech; поиск символа в библиотеке | листы схемы, проект для скачивания |
| `qet_tools`, `qet_call`, `qet_save` | пошаговая работа со схемой QElectroTech, когда нужны все её инструменты | результат каждого шага, сохранённые листы |
| `text_parse` | синтаксический разбор русских предложений; анализатор — параметром `parsers` ([russian.md](russian.md)) | готовый блок с деревом разбора, части речи и члены предложения |

Долгие (секунды–минуты) удобнее звать асинхронно — [api.md](api.md#асинхронные-вызовы).

## Свои файлы

| Инструмент | Зачем | Что в ответе |
|---|---|---|
| `files_upload` | загрузить свой файл: модель для Blender, проект QElectroTech, документ для проверки | ссылка `upload:<id>/<имя>` для аргументов инструментов |
| `files_publish` | показать свою загруженную картинку в документе (PNG, JPG, WebP, GIF, SVG) | ссылка `artifact:<id>/<имя>` и строка `![подпись](…)` |
| `files_unpublish` | снять свою опубликованную картинку — только если пользователь сам попросил | что снято |
| `files_list`, `files_delete` | свои файлы и занятое место; удалить ненужное | список со ссылками и размерами |
| `account_delete` | удалить свою учётную запись — только если пользователь сам попросил; в `confirm` — почта. Есть только в MCP и только с ключом учётной записи; в REST — `DELETE /api/v1/me` | что удалено |

Подробнее и через REST — [api.md](api.md#свои-файлы).

## Поделиться документом

| Инструмент | Зачем | Что в ответе |
|---|---|---|
| `document_share` | сохранить документ и получить ссылку на живую страницу — схемы кликаются, ноты играют; с тем же `id` — новая версия по той же ссылке | `url` — `https://v2.spiridus.ru/d/<id>`, `version`, `versionUrl` — ссылка на эту версию |
| `documents_list` | свои опубликованные документы | id, ссылка, заголовок, сколько версий |
| `documents_catalog` | одна ссылка на каталог всех своих документов — для человека, который запутался, что где; обновляется сам; `rotate: true` — новая ссылка | `url` каталога, сколько в нём документов |
| `document_delete` | удалить документ со всеми версиями — только если пользователь сам попросил | что удалено |

Подробнее — [api.md](api.md#поделиться-документом).

## Сборки песочниц: версии программ

Всё, что считает сервер, — в **сборке**: версия программы с набором модулей. У программы может быть
несколько сборок — разные версии (прежняя и новая на пробу) или разные варианты одной версии. Нужную
называют параметром `build` у инструмента или строкой `build:` в блоке документа; без неё берётся
сборка по умолчанию. Как это устроено, состояния сборок и переход на новую версию —
[blocks/sandbox.md](blocks/sandbox.md).

| Инструмент | Зачем |
|---|---|
| `fonts_list` | какие шрифты есть: свои Timashkovy GOST (состояние и сколько знаков каждого набора уже нарисовано) и сторонние шрифты сайта — с готовым блоком ```` ```font ```` (`file: fonts:<id>`); семейства шрифтов в сборках песочниц (FreeCAD: `font()`); `own: true` — только свои |
| `sandbox_builds` | какие сборки есть сейчас: программа, версия, вариант, модули, состояние (`default`, `stable`, `next`, `deprecated` с датой отключения); фильтры `program`, `version`, `module` |

предупреждает заранее, с датой.

## Для чатов: укороченное описание

Модели в чате (Open WebUI и т. п.) проще выбирать из меньшего числа операций. Для них —
`https://v2.spiridus.ru/api/v1/openapi-chat.json`: только инструменты модели, без служебных адресов.
Ещё короче — свой набор: `openapi-chat.json?tools=render_block_docs,render_examples,render_check`.
